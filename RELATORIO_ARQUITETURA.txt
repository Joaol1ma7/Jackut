RELATÓRIO SOBRE A ARQUITETURA DO PROJETO

Este documento descreve a arquitetura atual do projeto (pacote base: br.ufal.ic.jackut),
suas camadas, responsabilidades e decisões de projeto adotadas durante as últimas mudanças.

ESTRUTURA PRINCIPAL

A aplicação segue uma arquitetura em camadas com separação clara de responsabilidades.
As camadas principais são:

1. Camada de Apresentação
   - Representada pelos scripts de teste EasyAccept e pela classe `Main` que dispara
     as suites de testes. Essa camada atua como cliente da API oferecida pela Facade.

2. Camada de Facade
   - A classe `br.ufal.ic.jackut.Facade` é o ponto de entrada único para clientes e testes.
   - A Facade expõe operações de alto nível e delega para o serviço apropriado (`IUsuarioService`).

3. Camada de Serviço (Lógica de Negócio)
   - Implementada por `UsuarioService` (contrato `IUsuarioService`).
   - Contém validações, regras de negócio e coordena chamadas para o repositório.
   - Responsabilidades: gerenciamento de usuários, atributos de perfil, pedidos de amizade,
     recados e validações relacionadas.

4. Camada de Acesso a Dados (Repositório)
   - Definida pela interface `IUsuarioRepository` e implementada por `UsuarioRepository`.
   - O repositório mantém o armazenamento em memória durante a execução e é responsável
     por carregar/salvar o estado para a camada de persistência.

5. Camada de Persistência
   - Implementada com `XMLEncoder` e `XMLDecoder` do Java.
   - O arquivo de persistência padrão é `jackut_data.xml` (localizado na raiz do projeto).

FLUXO DE EXECUÇÃO (exemplo: criação de usuário)

1. Um teste ou cliente chama `Facade.criarUsuario(...)`.
2. A `Facade` valida parâmetros superficiais e delega para `IUsuarioService.criarUsuario(...)`.
3. `UsuarioService` aplica validações de negócio e, em caso de sucesso, utiliza `IUsuarioRepository`
   para persistir o usuário em memória.
4. `UsuarioRepository` atualiza a estrutura em memória e invoca a persistência (XMLEncoder)
   para salvar o mapa de usuários em `jackut_data.xml`.
5. Resultados e exceções são propagados de volta até a `Facade` e então ao cliente.

PADRÕES DE PROJETO

- Facade: fornece API simples e consolidada para clientes e testes.
- Repository: abstrai o acesso a dados e a persistência (interface `IUsuarioRepository`).
- Service: encapsula regras de negócio e orquestra repositórios (`IUsuarioService`).
- Dependency Injection: `UsuarioService` recebe `IUsuarioRepository` por construtor; `Facade`
  também permite injeção do serviço, facilitando testes e substituições.

PRINCÍPIOS SOLID (como foram aplicados)

Single Responsibility Principle (SRP)
  - Cada classe tem responsabilidade única: `Usuario` modela estado do usuário;
    `UsuarioService` contém regras de negócio; `UsuarioRepository` cuida da persistência;
    `Facade` expõe a API.

Open/Closed Principle (OCP)
  - As classes dependem de abstrações (`IUsuarioService`, `IUsuarioRepository`) e podem ser
    estendidas com novas implementações sem modificar o código cliente.

Liskov Substitution Principle (LSP)
  - Implementações de interfaces preservam o contrato esperado, permitindo substituição.

Interface Segregation Principle (ISP)
  - As interfaces são coesas e específicas (`IUsuarioService` concentra operações do domínio
    de usuário; `IUsuarioRepository` concentra operações de armazenamento).

Dependency Inversion Principle (DIP)
  - Camadas de alto nível (`Facade`, `UsuarioService`) dependem de abstrações, não de implementações
    concretas. Isso facilita testes e mudanças na persistência.


CONCLUSÃO

O projeto adota uma arquitetura em camadas com ênfase em separação de responsabilidades
e inversão de dependência.
